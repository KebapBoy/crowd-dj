# AGENTS.md

Instructions for AI coding agents (and humans) working on this repository. How to use and run it is in [README.md](README.md); **what to build and why is in [docs/concept.md](docs/concept.md)**. Read the concept before building a feature, and keep it current when a decision changes.

## Project

A web app (SvelteKit, TypeScript) for a shared music queue in a room: sessions that people join by link, pools and wishes per person, and a server-side engine that plays the next track in turns through one Spotify account. Only hosts sign in with Spotify (development mode allows 5 users per app); participants have profiles per browser.

## Conventions

- Node 26, npm. The only runtime dependency is the native libsql client; everything else is a devDependency that adapter-node bundles. Dependencies are pinned exactly (`save-exact`), and only versions that have been out for at least 14 days are installed (`min-release-age` in `.npmrc`); the same for the base image in the `Dockerfile`.
- Formatting: Prettier (`prettier.config.js`) with 4 spaces, no semicolons, opening braces on the same line; `.editorconfig` gives editors the same settings. Run `npm run format` before every commit (`npm run lint` checks it). `drizzle/` and `package-lock.json` are left to the tools that write them (npm takes the indentation of `package.json`).
- Svelte 5 runes everywhere. Server-only code lives under `src/lib/server/` or in `+page.server.ts` / `+server.ts`. Imports through `#lib/` name the file with its extension (`#lib/server/app.ts`); code under `src/lib/server/` that tests import must not import `$app/env/private` (take the values as parameters, as `accounts.ts` does; `app.ts` wires them up).
- Schema changes: edit `schema.ts`, run `npm run db:generate`, commit the new migration in `drizzle/`. The server applies it at start.
- Identifiers, comments and docs in English. **Every visible text goes through Paraglide** (`m.key()`) and gets both an English and a German message.
- Spotify: respect the limits in [docs/concept.md](docs/concept.md#spotify-platform-limits-why-it-is-built-this-way). Never re-stream audio, never call removed endpoints, look tracks up one at a time and cache them, poll only while a session is active, show cover art and metadata with anything that plays. Never use "Spotify" in the app's name.
- Settings are environment variables, declared in `src/env.ts`. Add every new one with a comment to `.env.example`, to `deploy/compose.yaml` and to the configuration table in the README.
- Secrets (client secret, `APP_SECRET`, tokens) never go into the repository or the logs. Stored Spotify tokens are encrypted with `APP_SECRET`.
- This repository is public. Use `example.com`, `192.0.2.x` and generic names in code, docs, tests and commit messages. Never commit real domains, IP addresses, Spotify user IDs, tokens, `.env` or a database.

## With every change

1. Add the change to `CHANGELOG.md` ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/)) under `## [Unreleased]`. A release turns that section into `## [x.y.z] - YYYY-MM-DD` under [Semantic Versioning](https://semver.org/spec/v2.0.0.html), sets `version` in `package.json`, is committed as `chore: release x.y.z` and tagged `v<x.y.z>`. MAJOR for changes that need action from people running it (settings, Spotify app setup, data), MINOR for new features, PATCH for fixes.
2. Update `README.md` when features, requirements, installation or configuration change, `docs/concept.md` when a decision changes, and this file when the layout or the conventions change.
3. Check: `npm run check`, `npm run lint`, `npm test`, `npm run build`, and for changes to the image `docker build .` and a request to `/healthz`.
4. Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `feat` (MINOR), `fix` (PATCH), `perf` (PATCH), `docs`, `refactor`, `test` or `chore` (no release); `!` after the type plus a `BREAKING CHANGE:` footer for MAJOR. Scopes where they help: `spotify`, `engine`, `session`, `pool`, `account`, `db`, `i18n`, `docker`, `dev`. Imperative, lower-case subject up to 72 characters; the body says what changes for the user and why.
